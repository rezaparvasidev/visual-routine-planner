# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — launch the app in development (electron-vite dev server + Electron, with HMR for the renderer)
- `npm run typecheck` — type-check both the main/preload process (`tsconfig.node.json`) and the renderer (`tsconfig.web.json`); run this after any change, there is no separate lint/test suite
- `npm run build` — typecheck then production-build all three processes via electron-vite (outputs to `out/`)
- `npm run dist` — build then package a Windows NSIS installer via electron-builder (outputs to `release/`)
- `npm run preview` — preview a production build without repackaging

There is no test runner or linter configured. `npm run typecheck` is the primary correctness gate.

Do not `npm run dev` / restart the running app while the user has it open testing changes live — HMR module-replacement mid-interaction has caused real instability (e.g. a store-module HMR update can desync a component from the live store). Prefer letting Vite's HMR apply your edit to their already-running window over force-restarting.

## Architecture

Electron + React + TypeScript app for visually building day routines (24-hour timelines with drag-and-drop time slots — no calendar dates anywhere). Three separate TypeScript build targets, wired together by `electron.vite.config.ts` (electron-vite), each with its own tsconfig:

- **`electron/`** — Node-capable main process (`main.ts`) and `preload.ts`. Never imported by the renderer directly. `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true` — the renderer talks to main only through `window.routinesAPI` (defined in `preload.ts` via `contextBridge`), which maps to `ipcMain.handle` calls registered in `electron/ipc/routinesHandlers.ts`. `main.ts` also sets the window/taskbar icon from `build/icon.ico` (generated by a one-off script, not part of the build pipeline — regenerate by hand in an image tool if it needs to change).
- **`src/`** — the renderer (React app), DOM-only, no Node APIs.
- **`shared/domain.ts`** — the `Routine`/`Slot`/`PersistedData` types, imported by both `electron/` and `src/` via the `@shared/*` path alias (also wired into both tsconfigs and the electron-vite config's per-target `resolve.alias`).

### Data flow / persistence

Single JSON file at `app.getPath('userData')/routines.json` (`electron/persistence/store.ts`), read/written only in the main process with atomic writes (write to `.tmp`, then rename). Renderer flow: `App` calls `store.init()` on mount → IPC `routines:load` → populates the zustand store (`src/state/routinesStore.ts`). Every store mutation is autosaved via a `subscribeWithSelector` subscription on `state.routines`, debounced 400ms, sending the *full* `PersistedData` object over IPC `routines:save` each time (not incremental diffs).

### Core domain logic lives outside React

All the actual scheduling rules are pure functions in `src/lib/slotOps.ts` (push-resize on drag, move, gap-finding, duplicate placement, delete) and `src/lib/time.ts` (minute↔percent/pixel conversion, snapping, view-range/duration formatting). These are framework-free and take/return `Routine` objects immutably. The zustand store (`src/state/routinesStore.ts`) is a thin dispatcher: every mutating action calls one of these pure functions and replaces the matching routine in the `routines` array. **When changing scheduling behavior (overlap handling, min durations, gap search order), edit `slotOps.ts`, not the components.**

Key invariants enforced by `slotOps.ts`:
- `Routine.slots` is always kept sorted ascending by `startMinutes`.
- Slots never overlap: dragging a slot edge into a neighbor pushes the neighbor's facing edge to match, down to the neighbor's own `MIN_SLOT_DURATION` floor — it does not cascade past the immediate neighbor. Moving a slot's body (`moveSlot`) instead just clamps within the gap bounded by its neighbors — it never pushes.
- The wake/sleep bounds (`routine.wakeMinutes`/`sleepMinutes`) can never be moved past the outermost slot's edge, so a slot can never end up orphaned outside the active range.
- "Add Slot" and "Duplicate" both fall back to `addSlotToGap`'s first-fit/shrink-to-fit gap search rather than silently failing when there's no room.
- `SNAP_MINUTES`, `MIN_SLOT_DURATION`, and `DEFAULT_SLOT_DURATION` (all in `lib/time.ts`) are all 30 — every time-related operation uses one shared unit, don't reintroduce a finer-grained one for just one of them.

### Two-timeline layout: overview vs. zoomed main track

Each routine renders two horizontal bars, both driven by the same `routine.wakeMinutes`/`sleepMinutes`:
- **`RoutineOverview.tsx`** — a thin full-day (0–1440 min) minimap. This is the *only* place wake/sleep are dragged (via `WakeSleepHandle`, which is otherwise unused elsewhere now).
- **`RoutineTimeline.tsx`**'s main track — zoomed to `computeViewRange(wake, sleep)` (wake/sleep ± `VIEW_PADDING_MINUTES`, clamped to the day), so slots aren't squeezed into a tiny fraction of a 24h bar. This view is not draggable; it only shows the padded blocked buffer as hatched `inactive-region`s. All slot positioning/drag math in `SlotBlock.tsx` and the click-drag-create logic in `RoutineTimeline.tsx` take `viewStart`/`viewEnd` and use `minutesToPercent`/`pixelsToMinutes` with that explicit range (not the default full-day range those functions fall back to).

`DAY_MARKER_MINUTES` (noon, 6pm) draws a fixed red reference line on both bars via `.marker-line`. That class intentionally has **no `z-index`** — it relies on DOM order (rendered before slots) to always stay behind them. Do not give it an explicit z-index without also checking `.slot-block.is-selected`'s (`z-index: 3`) — a marker line between "auto" and a selected slot's z-index would show through unselected slots but not selected ones (this exact bug shipped once).

### Slot interaction model

A slot has three independent gestures, all starting from `SlotBlock.tsx`:
- **Click (no drag) → select.** Selection is global, single-slot state in the store (`selectedSlot: {routineId, slotId} | null`), not local component state — so selecting a slot in one routine deselects any slot in another. A centered `.slot-tools` row (Color/Duplicate/Delete) appears *below* the slot (not overlapping the title) only while selected; Escape or clicking empty track space clears selection (see `App.tsx`'s global keydown handler and `RoutineTimeline.tsx`'s track pointerdown).
- **Drag the body → move.** Distinguished from a click via a small pixel threshold (`MOVE_THRESHOLD_PX`) before committing to a move; `moveSlot` clamps within the gap, never pushes neighbors.
- **Drag an edge → resize**, with push-into-neighbor per `resizeSlotEdge`.
- **Double-click the title → inline rename** (swaps the `<span>` for an `<input>` in place); color is changed via the toolbar's Color button opening `ColorPopover.tsx`, never automatically.

The title's font size adapts to fit: `SlotBlock.tsx` measures via a `ResizeObserver` and shrinks one step before falling back to the normal size + a native tooltip if even the smaller size doesn't fit. **The observer watches the title's *container* (`.slot-content`), not the title `<span>` itself** — the span shrinks to fit its own text and never reports a resize when the slot around it grows, which silently breaks "grow back after shrinking" if you observe the wrong element (this exact bug shipped once). A duration label (`formatDuration`) is always rendered under the title, independent of selection.

New slots (via "+ Add Slot" or click-drag-create) cycle through `PRESET_COLORS` (`lib/colors.ts`) via a module-level rotating index in `routinesStore.ts`, rather than always defaulting to one color. `duplicateSlot` keeps the original's color unchanged. `ColorPicker.tsx` also surfaces every custom (non-preset) color already used by *any* slot in *any* routine, so a custom color only has to be entered once — this list is derived with `useMemo` over the store's `routines` array; **do not compute it inline in the selector itself** (returning a fresh array from a zustand selector on every read trips React's `useSyncExternalStore` infinite-loop guard the moment the popover mounts — this exact bug shipped once).

`duplicateRoutine` deep-copies a routine (fresh id, `" (copy)"` name, fresh slot ids) and splices it in immediately after the original.
